# Архитектура MoscowRoleplay Voice

Документ описывает фундамент проекта, границы модулей и направления развития. Текущий этап — модульный монолит для одного VPS с 1 vCPU и 2 GB RAM.

## 1. Цели и ограничения

Цели:

- обеспечить запускаемую и проверяемую основу сервера и клиента;
- отделить инфраструктуру от будущей бизнес-логики;
- подготовить безопасный протокол и точки расширения;
- не усложнять систему раньше времени.

Ограничения первого этапа:

- один сервер, один экземпляр приложения;
- PostgreSQL на том же VPS;
- нет кластера, брокеров сообщений и микросервисов;
- нет авторизации, игровых интеграций и голосовой передачи;
- все чувствительные операции в будущем должны проверяться на сервере.

## 2. Почему модульный монолит

Модульный монолит выбран по следующим причинам:

1. **Ресурсы.** 1 vCPU и 2 GB RAM недостаточны для комфортного запуска множества сервисов, service mesh и брокеров.
2. **Простота эксплуатации.** Один процесс, один Docker-образ, одна база. Меньше точек отказа.
3. **Скорость разработки.** Изменения схемы и протокола не требуют синхронизации нескольких деплоев.
4. **Будущее разделение.** Модули уже разделены по каталогам и ответственности. Голосовой узел можно вынести отдельно, не переписывая HTTP-слой, конфигурацию и базу.
5. **Отсутствие доказанной необходимости.** Микросервисы, Redis, RabbitMQ, Kubernetes и Socket.IO не решают текущих задач и добавляют стоимость владения.

Монолит не означает «всё в одном файле». Точка входа `server/src/index.js` только собирает компоненты. Логика находится в профильных модулях.

## 3. Компоненты сервера

### 3.1. `config`

Файл: `server/src/config/index.js`.

Отвечает за:

- загрузку `.env` из корня проекта;
- приоритет переменных окружения над `.env`;
- проверку обязательных переменных;
- проверку диапазонов портов и таймаутов;
- проверку IP-адресов mediasoup;
- формирование неизменяемого объекта конфигурации.

Ошибки конфигурации содержат только имена переменных и правила, но не значения. Пароль PostgreSQL проверяется на минимальную длину и никогда не логируется. В `production` дополнительно запрещены пароли-заглушки (`change_me_*` и аналогичные) и совпадение `POSTGRES_PASSWORD` с `POSTGRES_USER` или `POSTGRES_DB`. В `development` и `test` заглушки допустимы.

### 3.2. `utils/logger`

Файл: `server/src/utils/logger.js`.

Структурированные JSON-логи `pino`:

- базовые поля `service`, `version`, `env`;
- маскирование паролей, токенов, `authorization` и `cookie`;
- человекочитаемый режим `pino-pretty` только вне production.

Правило: не логировать содержимое WebSocket-сообщений, токены, пароли и персональные данные.

### 3.3. `http`

Файл: `server/src/http/server.js`.

Встроенный HTTP-сервер Node.js без лишнего фреймворка:

- `GET /health/live` — liveness: процесс HTTP-сервера работает, PostgreSQL не проверяется;
- `GET /health/ready` — readiness: сервер готов обслуживать запросы, включая доступность PostgreSQL;
- `GET /health` — совместимый с Docker healthcheck маршрут, работает как readiness-проверка;
- `GET /` — краткие сведения о сервисе и ссылки на health-маршруты;
- `404` и `405` с JSON-ошибками;
- security-заголовки;
- `X-Request-Id` для диагностики;
- таймауты запросов и заголовков;
- безопасная обработка ошибок без утечки внутренних деталей.

Liveness возвращает `200`, пока процесс способен обработать запрос, и не зависит от PostgreSQL. Readiness возвращает `200`, если база доступна, и `503`, если база недоступна. Текст ошибки PostgreSQL и параметры подключения в ответ не попадают.

При старте сервер сначала проверяет подключение к PostgreSQL и завершается, если база недоступна; это осознанная зависимость запуска, а не liveness-проверка. После успешного запуска падение базы не останавливает HTTP-сервер: liveness продолжает отвечать `200`, readiness переходит в `degraded`.

### 3.4. `websocket`

Файл: `server/src/websocket/server.js`.

WebSocket-шлюз на `ws`:

- подключение к тому же HTTP-серверу по пути `WS_PATH`;
- ограничение `maxPayload`;
- запрет двоичных сообщений;
- парсинг JSON и строгая проверка полей через `shared/protocol.js`;
- ограничение частоты сообщений;
- счётчик нарушений и закрытие соединения при злоупотреблении;
- heartbeat через ping/pong;
- безопасная обработка `close` и `error`;
- корректное закрытие при остановке сервера.

На текущем этапе поддерживаются только `client.ping` и служебные ответы. Авторизация и голосовые сообщения не реализованы.

### 3.5. `database`

Файлы:

- `server/src/database/pool.js` — пул `pg`, проверка подключения, health-check, закрытие;
- `server/src/database/migrations.js` — применение SQL-миграций;
- `server/src/database/migrate-cli.js` — CLI для миграций.

Пул ограничен по количеству соединений и таймаутам. Ошибки простаивающих клиентов логируются. Пароль не выводится.

Миграции:

- применяются по порядку имён;
- хранят контрольную сумму в `schema_migrations`;
- выполняются в транзакции;
- защищены advisory lock от параллельного запуска;
- не изменяют уже применённые файлы.

На первом этапе создаётся только служебная таблица `service_metadata`. Бизнес-схема появится позже.

### 3.6. `monitoring`

Файл: `server/src/monitoring/health.js`.

Формирует два независимых ответа:

- liveness (`checkLiveness`) — статус `ok`, версия, окружение, uptime и состояние процесса; база данных не проверяется;
- readiness (`checkReadiness`) — дополнительно результат проверки PostgreSQL с задержкой; при недоступной базе статус `degraded`;
- безопасный код ошибки без деталей подключения и без текста ошибки PostgreSQL.

### 3.7. `utils/shutdown`

Файл: `server/src/utils/shutdown.js`.

Менеджер корректной остановки:

- обработчики вызываются в порядке регистрации;
- сначала закрывается WebSocket, затем HTTP, затем PostgreSQL;
- ошибка одного обработчика не прерывает остановку остальных;
- при превышении таймаута процесс завершается принудительно;
- повторный вызов игнорируется.

Точка входа регистрирует обработчики `SIGINT` и `SIGTERM`, а также централизованно обрабатывает `unhandledRejection` и `uncaughtException`.

### 3.8. Зарезервированные бизнес-модули

| Модуль | Будущая ответственность | Текущее состояние |
|---|---|---|
| `auth` | Discord OAuth2, сессии, связка аккаунтов | Только README |
| `game` | PRC API V2, проверка Roblox-аккаунта | Только README |
| `voice` | mediasoup Worker, Router, Transport | Только README и конфигурация |
| `proximity` | Расчёт слышимости по расстоянию | Только README |
| `radio` | Радиоканалы, PTT, права | Только README |

Фиктивных реализаций нет: если функция не готова, она отсутствует и задокументирована.

## 4. Общий протокол

Файл: `shared/protocol.js`.

Формат:

```json
{
  "v": 1,
  "type": "client.ping",
  "id": "необязательный_идентификатор",
  "data": {
    "nonce": "необязательная_строка"
  }
}
```

Правила:

- `v` обязательна и равна `PROTOCOL_VERSION`;
- `type` обязателен и входит в белый список;
- `id` необязателен, но если указан — только `[A-Za-z0-9_-]`, до 64 символов;
- `data` необязательна, но если указана — только объект;
- неизвестные поля запрещены;
- размер сообщения ограничен;
- двоичные сообщения запрещены.

Серверные типы:

- `server.hello` — параметры соединения;
- `server.pong` — ответ на ping;
- `server.error` — машиночитаемый код и русское сообщение.

Протокол не зависит от Node.js или браузера. Для корректной работы ES Modules в каталоге `shared` есть собственный `package.json` с `"type": "module"`.

## 5. Потоки выполнения

### 5.1. Запуск

```text
index.js
  → loadConfig()
  → createLogger()
  → createDatabase().connect()
  → createHttpServer()
  → createWebSocketGateway()
  → listen()
  → регистрация graceful shutdown
```

Если подключение к базе не удалось, сервер не запускается и завершается с кодом `1`.

### 5.2. HTTP-запрос

```text
HTTP-запрос
  → security-заголовки и requestId
  → маршрутизация
  → health-check (при необходимости)
  → JSON-ответ
  → структурированный лог
```

Тело запроса не читается: на текущем этапе нет API, принимающего тело. Это уменьшает поверхность атаки.

### 5.3. WebSocket-сообщение

```text
WebSocket frame
  → maxPayload (ws)
  → проверка binary
  → ограничение частоты
  → JSON.parse
  → проверка конверта и data (shared/protocol.js)
  → обработчик типа
  → ответ или server.error
```

При превышении лимита нарушений соединение закрывается с кодом `1008`.

### 5.4. Миграции

```text
npm run migrate
  → config + logger
  → database.connect()
  → advisory lock
  → CREATE TABLE schema_migrations
  → чтение *.sql по порядку
  → проверка контрольной суммы
  → BEGIN / SQL / INSERT / COMMIT
  → unlock
```

## 6. Данные и PostgreSQL

Правила хранения:

- PostgreSQL хранит только долговременные данные: аккаунты, связки, права, конфигурацию каналов.
- Игровые координаты, тики близости и временные метрики не сохраняются в PostgreSQL при каждом обновлении.
- Оперативные данные будут храниться в памяти процесса или в будущем специализированном хранилище только после доказанной необходимости.
- Окончательная бизнес-схема не создаётся на этапе фундамента.

Текущая миграция `0001_bootstrap.sql` создаёт `service_metadata` — служебную таблицу без игровых данных.

## 7. Безопасность

### Сервер

- Клиент не считается доверенным.
- Все входящие сообщения валидируются.
- Размер и частота сообщений ограничены.
- Секреты не попадают в логи.
- PostgreSQL не публикуется наружу.
- Health-check не раскрывает внутренние ошибки.
- Внутри Docker-сети PostgreSQL используется без SSL (`POSTGRES_SSL=false`). Для публичного подключения требуется TLS с проверкой сертификата; `POSTGRES_SSL=true` не включается автоматически.
- Docker-контейнер сервера работает от пользователя `node`, с `no-new-privileges`.

### Electron

- `contextIsolation: true`;
- `nodeIntegration: false`;
- `sandbox: true`;
- renderer не получает `require`, `process`, `ipcRenderer` или файловую систему;
- preload экспортирует только `getAppInfo`;
- внешние переходы и новые окна запрещены;
- все разрешения браузера по умолчанию запрещены;
- CSP не разрешает внешние источники.

Для будущего микрофона потребуется отдельное явное разрешение только для локального renderer-файла приложения. Это будет сделано на этапе голосового клиента.

## 8. Docker и mediasoup

Docker Compose:

- PostgreSQL не публикуется наружу;
- сервер публикует TCP-порт приложения и UDP-диапазон mediasoup;
- PostgreSQL имеет healthcheck и постоянный volume;
- сервер имеет healthcheck и ждёт здоровую базу;
- логи ограничены `10 MB × 3`;
- контейнеры перезапускаются `unless-stopped`;
- используется bridge-сеть, без `host network`.

mediasoup:

- конфигурация диапазона UDP и публичного IP уже есть в `.env`;
- Docker Compose публикует диапазон UDP;
- `MEDIASOUP_ANNOUNCED_IP` на текущем этапе может быть пустым; перед развёртыванием голосового модуля укажите публичный IP VPS, но не `127.0.0.1`;
- Worker пока не создаётся;
- на 1 vCPU достаточно одного Worker;
- при росте нагрузки голосовой узел можно вынести на отдельный VPS.

Почему не `host network`: bridge-сеть с явным publish-портом достаточно для текущей схемы и не ломает изоляцию контейнеров. `host network` допустим только при доказанной проблеме с производительностью или NAT, но не на этапе фундамента.

## 9. Точки будущего масштабирования

1. **Отдельный voice node.** Вынести `voice` в сервис mediasoup на другом VPS. Control plane остаётся на основном сервере, а клиент получает параметры подключения к нужному узлу.
2. **Несколько Worker.** На многоядерном VPS запускать несколько mediasoup Worker, по одному на ядро.
3. **Разделение комнат.** Router на комнату или крупный канал, чтобы изолировать нагрузку.
4. **Кэш состояния.** Если оперативные данные перестанут помещаться в память, добавить специализированное хранилище только после измерений.
5. **Очередь событий.** Если появится несколько независимых потребителей игровых событий, рассмотреть брокер сообщений. Сейчас он не нужен.
6. **Наблюдаемость.** Добавить метрики, трассировку и централизованные логи при появлении нескольких узлов.

Все эти шаги должны сопровождаться измерениями. Не добавлять инфраструктуру «на будущее» без доказанной необходимости.

## 10. Границы текущего этапа

Архитектура специально оставляет пустые границы для:

- Discord OAuth2;
- Bloxlink;
- PRC API V2;
- Proximity;
- Radio;
- PTT;
- mediasoup signaling;
- передачи голоса.

Эти функции не реализованы и не имитируются. Следующий этап начинается только после отдельной команды владельца проекта.
