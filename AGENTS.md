# Правила работы над MoscowRoleplay Voice

Этот файл обязателен для всех агентов и разработчиков, работающих с проектом через OpenCode, Kilo CLI или вручную. Правила действуют до их явного изменения владельцем проекта.

## 1. Язык общения и документации

- Все ответы пользователю, отчёты, вопросы и пояснения — только на русском языке.
- Вся документация (`README.md`, `docs/*`, комментарии в коде, сообщения об ошибках для пользователя) — на русском языке.
- Названия переменных, функций, классов, файлов, npm-пакетов, API, протоколов и технических идентификаторов остаются на английском языке, если это общепринятая практика.
- Английские технические термины разрешены, но при первом употреблении их смысл нужно объяснять по-русски.
- Нельзя переходить на английский в ответах пользователю без его прямой просьбы.

## 2. Назначение проекта и текущий этап

MoscowRoleplay Voice — голосовая система для Roblox ER:LC проекта MoscowRoleplay. В целевой версии она должна обеспечивать:

- голосовое общение по близости (Proximity Voice);
- радиоканалы, включая отдельные каналы государственных структур;
- авторизацию через Discord;
- связывание Discord-аккаунта с Roblox-аккаунтом;
- проверку игрока на сервере ER:LC через PRC API V2;
- Windows-клиент с графическим интерфейсом;
- серверную проверку прав и обработку голосовых соединений.

**Текущий статус — этап 5/5: интеграция сервера и клиента завершена.** Реализованы Discord OAuth2, Bloxlink, PRC API V2, Proximity Engine, Radio Engine, PTT, mediasoup signaling, интерфейс Electron и передача голоса.

Проект разделён на две независимые части: `app/` — Windows-клиент, `server/` — сервер и его развёртывание. Новые крупные этапы, изменение архитектуры и добавление технологий — только по прямой команде владельца проекта.

## 3. Технологический стек

Сервер:

- Node.js 24 LTS (совместимая актуальная LTS-ветка);
- JavaScript ES Modules;
- mediasoup v3;
- WebSocket (`ws`);
- PostgreSQL;
- Docker и Docker Compose.

Клиент:

- Electron;
- JavaScript, HTML, CSS;
- mediasoup-client;
- Web Audio API.

Серверная ОС: Ubuntu Server 24.04 LTS.
Среда разработки: Windows 10, PowerShell, Node.js, npm, Git, Docker Desktop с Linux-контейнерами (если доступен).

Запрещено добавлять LiveKit, Socket.IO, Redis, Kubernetes, RabbitMQ, Python и другие технологии без доказанной необходимости и согласования. Python запрещён как runtime и как инструмент сборки.

## 4. Архитектурные правила

- На первом этапе используется **модульный монолит**. Не создавать микросервисы, кластеры, брокеры сообщений и оркестраторы.
- Вся логика не должна находиться в `server/src/index.js`. `index.js` отвечает только за сборку компонентов и запуск.
- Модули сервера разделяются по ответственности:
  - `config` — загрузка и валидация конфигурации;
  - `database` — подключение к PostgreSQL и миграции;
  - `websocket` — WebSocket-транспорт и валидация сообщений;
  - `monitoring` — health-check и наблюдаемость;
  - `utils` — общие утилиты без бизнес-логики;
  - `auth`, `game`, `voice`, `proximity`, `radio` — реализованные бизнес-модули.
- Общий протокол клиента и сервера: канонический `server/shared/protocol.js`, копия `app/shared/protocol.js`. Не дублировать формат сообщений в разных местах. Синхронизация — `npm run shared:sync` в папке `server`.
- Зависимости между модулями должны быть направлены от инфраструктуры к бизнес-логике. Бизнес-модули не должны напрямую управлять HTTP-сервером или пулом PostgreSQL.
- Не создавать фиктивные реализации mediasoup, Discord, Bloxlink или PRC API. Если функция ещё не реализована, это должно быть явно задокументировано, а не имитировано.
- Не хранить игровые координаты и временные игровые метрики в PostgreSQL при каждом обновлении. Для оперативных данных в будущем использовать память процесса или специализированное хранилище только после доказанной необходимости.
- Схема базы данных должна развиваться через миграции. Окончательная бизнес-схема на текущем этапе не создаётся.
- Архитектура должна допускать будущее выделение голосовых узлов, но сейчас не нужно реализовывать кластер.

## 5. Безопасность

### Секреты

- Никогда не читать, не выводить в чат, не логировать и не коммитить содержимое `.env`, токены, пароли, приватные ключи и другие секреты.
- Для примеров использовать только `.env.example` с безопасными заглушками.
- Не выводить значения переменных окружения в отчётах и логах. Допустимо указывать только имена переменных.
- Не добавлять секреты в Git-историю. При случайном попадании секрета немедленно сообщить владельцу и не выполнять необратимые операции без согласия.

### Сервер

- Валидировать все входящие данные, включая WebSocket-сообщения.
- Ограничивать размер WebSocket-сообщений и частоту сообщений.
- Не доверять данным клиента: права, местоположение и роли всегда проверяются на сервере.
- Не логировать содержимое сообщений, токены, пароли и персональные данные.
- Корректно обрабатывать отключения клиентов и ошибки базы данных.
- Не публиковать PostgreSQL наружу без необходимости.
- Не использовать `host network` без технического обоснования.

### Electron

- `contextIsolation: true`;
- `nodeIntegration: false`;
- `sandbox: true`, если это не ломает необходимую функциональность;
- безопасный `preload.js`, экспортирующий только минимальный whitelist API;
- renderer не получает прямого доступа к Node.js, `require`, `ipcRenderer` и файловой системе;
- запрещены переходы на внешние URL и открытие новых окон без явной проверки.

### Git

- Исключать `.env`, секреты, `node_modules`, временные и сборочные файлы.
- Перед существенными изменениями проверять `git status`.
- Не удалять пользовательские изменения и не выполнять `git reset --hard`.
- Не переписывать историю Git.
- Не выполнять необратимые операции без согласия владельца.

## 6. Запрет на выдуманные API и результаты

- Не придумывать endpoints, поля API, версии библиотек и форматы ответов. Проверять официальную документацию и npm registry.
- Не утверждать, что проверка выполнена, если она не запускалась.
- Не скрывать ошибки и ограничения среды.
- Если Docker, PostgreSQL, WSL2 или нативная сборка недоступны, прямо указать это в отчёте и объяснить, какая проверка осталась невыполненной.
- Не выдавать успешный запуск одного компонента за успешную проверку всей системы.

## 7. Порядок работы с Git

1. Перед изменениями выполнить `git status`.
2. Не трогать чужие незакоммиченные изменения.
3. Делать осмысленные коммиты на русском или английском языке в формате Conventional Commits, например `feat: завершить интеграцию сервера и клиента`.
4. Не коммитить `.env`, секреты, `node_modules`, логи, дампы базы.
5. Не использовать `git reset --hard`, `git push --force`, rebase опубликованной истории и другие необратимые операции без прямого согласия.
6. После завершения этапа показать список изменённых файлов и подготовить отдельный коммит.
7. Не начинать следующий этап разработки без команды владельца.

## 8. Совместная работа OpenCode и Kilo CLI

- Оба инструмента обязаны прочитать этот файл перед изменениями.
- Не изменять `opencode.json` и настройки подключения к Kilo Gateway без необходимости.
- Не создавать конфликтующие конфигурации агентов. Общие правила хранятся в этом файле.
- Любой агент должен оставлять проект в запускаемом состоянии и обновлять документацию при изменении поведения.
- Если инструмент не может выполнить проверку, он обязан честно сообщить об этом, а не имитировать результат.
- Комментарии в коде и документация — на русском языке; идентификаторы — на английском.

## 9. Соглашения по коду

- Сервер: ES Modules, `import`/`export`, без `require`.
- Клиент Electron: CommonJS для main/preload, если нет веской причины использовать ESM.
- Отступы: 2 пробела.
- Точки с запятой: обязательны.
- Строки: одинарные кавычки, кроме JSON и HTML.
- Имена файлов: `kebab-case` или `camelCase` в соответствии с окружающим кодом.
- Ошибки: использовать коды в стиле `snake_case`, сообщения для пользователя — на русском языке.
- Логи: структурированные JSON-логи через `pino`; в разработке допускается `pino-pretty`.
- Не добавлять зависимости без необходимости. Перед добавлением проверять версию, совместимость и поддержку.

## 11. Определение готовности изменения

Изменение считается готовым, если:

- код запускается;
- синтаксис проверен;
- документация обновлена на русском языке;
- секреты не попали в файлы и логи;
- выполненные проверки перечислены честно;
- известные ограничения явно указаны;
- не нарушены границы текущего этапа.
